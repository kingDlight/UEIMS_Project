2.4 Non-UI Functions
#
Feature
System Function
Description
1
Security & Auth
JWT Validator & Blacklist
Intercepts API requests to verify JWT signature and expiration. Crucially, it cross-references the token's JTI against the invalidated_tokens database table to reject tokens that were logged out, ensuring strict stateless security (BR-03).
2
Security & Auth
Password Reset Token Generator
An API service that generates a cryptographically secure, time-sensitive (e.g., 24-hour) unique token when a user requests a password reset.
3
Notification
SMTP Email Dispatcher
A background messaging service responsible for formatting and sending external emails (e.g., Account Creation credentials, Password Reset links, and Late Report Warnings).
4
Training Management
Semester State Machine
A database-level trigger/service that automatically freezes related application and job posting data (making it immutable) when a Training Manager updates the semester status to LOCKED (BR-14).
5
Incident & Grading
Automated Warning Cron Job
A scheduled batch job (running daily) that scans the weekly_reports table against the deadline. It automatically flags students who missed reports or received consecutive REJECTED statuses, feeding data to the At-Risk Students List.
6
Student Supervision (Ent)
Evaluation Auto-Calculation
A backend logic function that automatically calculates the total Enterprise score based on the 4 Rubrics criteria (Attitude, Professionalism, Soft Skills, Progress) as soon as the Enterprise submits the evaluation form.
7
Incident & Grading
PDF Generation Service
An internal service utilizing a PDF generation library (e.g., iText) to dynamically render the Final Grade Report template, populating it with student grades before sending the file stream to the Training Manager's browser.
8
File Management
File Sanitization & Storage Service
An API middleware that validates uploaded CVs and Evidence files (checking for PDF/image extensions and enforcing the 5MB limit) before storing them securely in the storage bucket.
9
Student Application
Profile Matching Engine
A background data-processing function that cross-references a student's technical skill tags (from their profile) against the required skills of active job postings to generate a sorted "Compatibility Score" on the Job Board.

1. Common Functions & System Administration 
1.1 UC-01_Log into the system 
a. Functional Description 
UC ID and Name:
 UC-01 Log into the system 
Created By:
 QuangND
Date Created:
19/May/2026 
Primary Actor:
 All Actors 
Secondary Actors:
None 
Trigger:
User accesses the Login page of the UEIMS. 
Description:
Allows users to authenticate their identity to access the system using their registered internal accounts. 
Preconditions:
PRE-1: User account has been created and authorized in the system. 
Postconditions:
POST-1: User logs in successfully, system returns a Stateless JWT Access Token (containing User ID and mapped Permissions), and redirects to the Dashboard. 
POST-2: The system tracks the successful login in the System Log..
Normal Flow:
1.0 Login with an internal account
1. User enters Email and Password into the form and clicks the "Login" button. 2. System validates the login credentials (see 1.0.E1, 1.0.E2) and generates a secure JWT payload. 
3. System logs the action and redirects the user to the Dashboard
Alternative Flows:
None 
Exceptions:
1.0.E1 Incorrect login credentials
1. System displays an error message: "Invalid email or password."
2. If failed 5 consecutive times, the system locks the account (BR-01).
3. User is prompted to re-enter credentials.
1.0.E2 Account is deactivated
1. System displays an error message: "Your account has been locked. Please contact the Admin." 
2. Use case terminates.
Priority:
High, Must Have  
Frequency of Use:
Very High (Every user session)
Business Rules:
BR-01, BR-02, BR-03 
Other Information:
Passwords must never be transmitted as plain text. Passwords are securely hashed (BCrypt) in the database
Assumptions:
Assume that users remember their registered email addresses. 
b. Business Rules
ID
Business Rule
Business Rule Description
BR-01 
Account Lockout
User accounts are temporarily locked for 30 minutes after 5 consecutive failed login attempts.
BR-02 
Simultaneous Session Control
A user can only maintain one active session. Logging in from a new device invalidates the previous session.
BR-03
Token Expiration
User session tokens automatically expire after 15 minutes of complete inactivity.
1.2 UC-02_Log out
a. Functional Description 
UC ID and Name:
 UC-02 Log out  
Created By:
 QuangND
Date Created:
19/May/2026 
Primary Actor:
 All Actors 
Secondary Actors:
None 
Trigger:
User clicks the "Logout" button on the system header or profile menu. 
Description:
Destroys the user's active session by adding the JWT to the Blacklist table and redirects them back to the Login page.. 
Preconditions:
PRE-1: User is currently logged into the system. 
Postconditions:
POST-1: The user's JWT ID (jti) is added to the invalidated_tokens blacklist.
POST-2: User is restricted from accessing internal pages without authenticating again.
Normal Flow:
2.0 System Logout 
1. User clicks the "Logout" button. 
2. System calls the authentication service to insert the active token JTI into the invalidated_tokens table. 
3. System redirects the user to the Login page.
Alternative Flows:
None 
Exceptions:
None 
Priority:
High, Must Have  
Frequency of Use:
High (Every time a user finishes a session).
Business Rules:
BR-03
Other Information:
If the token is a JWT, it is appended to the server-side token blacklist until its natural expiration time to prevent reuse. 
Assumptions:
None
b. Business Rules
ID
Business Rule
Business Rule Description
BR-03
Token Expiration
User session tokens automatically expire after 15 minutes of complete inactivity.
1.3 UC-03_Forgot password
a. Functional Description 
UC ID and Name:
UC-03 Forgot password 
Created By:
 QuangND
Date Created:
19/May/2026 
Primary Actor:
 All Actors 
Secondary Actors:
Email System (SMTP) 
Trigger:
User clicks the "Forgot Password?" link on the Login screen. 
Description:
Allows internal account users to request a password reset link via email when they forget their credentials.
Preconditions:
None
Postconditions:
POST-1: A secure, time-sensitive password reset link is generated and dispatched to the user's email. .
Normal Flow:
3.0 Request password reset
1. User enters their registered Email address and clicks the "Send Request" button.
2. System verifies the existence of the email address in the database (see 3.0.E1).
3. System generates a secure, unique reset Token.
4. System dispatches an email containing the reset link embedded with the Token.
5. System displays a success message instructing the user to check their inbox.
Alternative Flows:
None 
Exceptions:
3.0.E1 Email does not exist (Branches from step 2 of 3.0)
1. System displays an error message: "Email address not found in the system."
2. User is prompted to re-enter the email address (rejoins step 1 of 3.0).
Priority:
High, Must Have  
Frequency of Use:
Low
Business Rules:
None
Other Information:
To mitigate user enumeration attacks, the system response time remains consistent regardless of whether the email exists.
Assumptions:
The external SMTP server configuration is valid and operational.
b. Business Rules
None
1.4 UC-04_Reset password 
a. Functional Description 
UC ID and Name:
UC-04 Reset password
Created By:
 QuangND
Date Created:
19/May/2026 
Primary Actor:
 All Actors 
Secondary Actors:
None 
Trigger:
User clicks the reset link received in their email, or logs in for the first time with an Admin-issued temporary account. 
Description:
Enforces the user to configure a new password to restore or secure account access.
Preconditions:
PRE-1: The security token contained within the URL parameters must be valid and unexpired.
Postconditions:
POST-1: The new password is encrypted and updated in the database.
POST-2: The specific reset token is permanently invalidated.
Normal Flow:

IV. Appendix
1. Assumptions
1.1. Organizational & Business Assumptions:
A1. Formal University-Enterprise Partnerships: It is assumed that the University has established formal, legally binding partnership agreements (MOU/MOA) with all participating Enterprises before they are registered and approved on the system by the Training Manager. The system does not verify or manage these legal agreements; it only tracks the digital approval status.
A2. User Computer Literacy & Internet Access: It is assumed that all 4 types of system users (System Admin, Training Manager, Enterprise representative, and Student) possess at minimum basic computer literacy skills — including the ability to navigate web browsers, fill out online forms, upload/download files, and manage email accounts. All users are also assumed to have stable and reliable internet access during their usage sessions.
A3. Enterprise Commitment to Intern Development: It is assumed that approved Enterprises will genuinely commit to providing meaningful, real-world projects and professional tasks for the interns throughout the entire duration of the internship semester. The system cannot enforce or verify the quality of the actual work assigned to students at the enterprise premises.
A4. Truthfulness of Student Data: It is assumed that all information provided by Students in their profiles, uploaded CVs, weekly reports, and final internship reports is truthful, accurate, and represents their own original work. The system does not incorporate plagiarism detection or identity verification mechanisms.
A5. Timely Enterprise Engagement: It is assumed that Enterprise representatives will log into the system at regular intervals (at minimum weekly) to review student weekly reports, provide feedback, update interview results, and complete the final Rubrics evaluation before the semester deadline. The system provides notification reminders but cannot force user engagement.
A6. Timely Training Manager Engagement: It is assumed that the Training Manager will actively monitor the system dashboard, process pending enterprise registrations, review at-risk student alerts, handle incident reports, and submit final academic grades within the timeframes defined by the academic calendar. Delays in TM actions may cascade into delayed student grade finalization.
1.2. Technical Assumptions:
A7. Standardized Evaluation Criteria: It is assumed that the University's grading scale (0.0 to 10.0) and the 4-criteria Rubrics framework (Attitude 20%, Professionalism 40%, Soft Skills 20%, Progress 20%) are officially standardized by the University's Academic Board and will remain unchanged during the lifetime of an active semester. Any mid-semester changes to the grading formula would require a system update.
A8. Prompt Interview Result Updates: It is assumed that Enterprise representatives will promptly update the Pass/Fail interview outcome on the system (UC-40) within 3 business days after conducting interviews. Delayed updates may block subsequent workflow steps (e.g., supervisor assignment, training plan creation).
A9. Accurate Semester Data from University: It is assumed that the academic semester information (semester number 1-9) assigned to each student in the university's core database is accurate and up-to-date at the time of Excel import (UC-20). Incorrect semester data would result in students receiving wrong permission levels on the platform.
A10. Honest Student Feedback: It is assumed that Students will provide honest and constructive feedback when evaluating their host Enterprise (UC-50). Since feedback is non-anonymous (the student's identity is recorded), it is assumed that students will not be pressured or intimidated by Enterprises regarding their feedback submissions. The confidentiality of feedback data (visible only to Training Manager) is designed to mitigate this risk.
2. Dependencies
2.1. Infrastructure Dependencies:
D1. Cloud Hosting Infrastructure: The system's availability, performance, and uptime depend entirely on the reliability of the chosen cloud hosting provider (e.g., AWS EC2/RDS, Microsoft Azure, Google Cloud Platform, or University-managed on-premise servers). The system requires a minimum guaranteed uptime of 99.5% during active semester periods to ensure uninterrupted access for all 4 user roles.
D2. Relational Database Management System (RDBMS): The system depends on PostgreSQL (version 14 or higher) as the primary persistent data store. All business-critical data — including user accounts, semester configurations, applications, weekly reports, evaluations, and feedback — is stored in this database. Database backup and disaster recovery procedures must be established by the infrastructure team.
2.2. External Service Dependencies:
D3. Email/SMTP Delivery Service: The system relies on a third-party email delivery service (e.g., SendGrid, AWS SES, or a University-managed SMTP server) for dispatching critical system communications, including: account creation credentials, password reset links, interview schedule notifications, late report warning alerts, and incident report notifications. If the email service is down, users will not receive time-sensitive notifications.
D4. External Video Conferencing Platforms: For the interview scheduling module (UC-39), the system stores and displays external meeting links (Google Meet, Zoom, Microsoft Teams) but does not host or manage the actual video call infrastructure. The availability and functionality of these platforms are outside the system's control.
D5. PDF Generation Libraries: The system depends on stable, well-maintained third-party libraries (e.g., iText for Java/Spring Boot, or PDFKit/Puppeteer for Node.js) to accurately generate and format downloadable PDF documents for: Final Grade Reports (UC-66), student CV downloads, and final internship report exports. Library version updates or deprecations may require code adjustments.
2.3. Data Source Dependencies:
D6. Core University Academic Database: The initial student onboarding process depends on the University's core academic system to provide an accurate, verified Excel file containing the baseline data of eligible students, including: Student ID, Full Name, Major, GPA, and Current Semester (1-9). The UEIMS does not independently verify this data against the university's records after import.
D7. Predefined Excel Import Template: The bulk import feature (UC-20) strictly depends on the Training Manager uploading student data using a predefined, version-controlled Excel template (.xlsx). Deviations from the template structure (e.g., missing columns, incorrect data types, extra sheets) will cause the import parser to reject the file and display specific validation error messages.
2.4. Data Source Dependencies:
D8. Internal Authentication & Authorization Framework: Since third-party Single Sign-On (SSO) providers are excluded from the current project scope, the system relies entirely on its own internal security stack for user authentication and role-based authorization. This includes: JWT (JSON Web Token) for session management, BCrypt algorithm for one-way password hashing, and a custom RBAC (Role-Based Access Control) middleware that enforces permissions for all 4 roles (Admin, Training Manager, Enterprise, Student).
3. Limitations
3.1. Performance & Storage Limitations:
L1. File Upload Size Restriction: To optimize server storage costs and prevent abuse, all file uploads across the system (student CV PDFs, incident evidence screenshots, final internship report PDFs) are strictly limited to a maximum of 5MB per individual file. Files exceeding this limit will be rejected at the API level with a clear error message.
L2. Data Export Volume Cap: To prevent server memory overload during large data extraction operations, all export-to-Excel and export-to-PDF functions are capped at a maximum of 10,000 records per single export transaction. If the dataset exceeds this threshold, the user must apply filters to reduce the record count before exporting.
L3. Concurrent User Capacity: The system is designed and load-tested to support up to 500 concurrent active sessions under normal operating conditions. Performance degradation (slower response times, increased latency) may occur during peak usage periods if concurrent sessions significantly exceed this threshold.
3.2. Feature & Functionality Limitations:
L4. No Real-Time Messaging or Chat: The system does not include an integrated, real-time chat or instant messaging module (comparable to Slack, Microsoft Teams, or Facebook Messenger). All communication between users is strictly asynchronous and channeled through formal text areas within the system (e.g., report feedback fields, incident description areas, announcement posts).
L5. No Native Video Interview Hosting: The system does not host, record, or manage native video or audio calls for enterprise recruitment interviews. The interview scheduling module (UC-39) only stores metadata — specifically the scheduled date/time and an external meeting link (e.g., a Zoom or Google Meet URL). The actual interview execution occurs entirely outside the UEIMS platform.
L6. Basic Statistical Analytics Only: The Training Manager's statistics dashboard (UC-26) provides only fundamental, pre-built statistical visualizations, including: interview pass/fail rates, student distribution by major/enterprise, and grade distribution histograms. The system does not feature advanced analytics capabilities such as AI-driven predictive models, trend forecasting, natural language processing of report content, or custom query builders.
L7. No Offline Functionality: As a purely web-based platform, the UEIMS requires a continuous, active internet connection for all operations. Users cannot perform any system tasks (submitting reports, grading students, reviewing applications) while disconnected. There is no local data caching, offline mode, or background synchronization mechanism.
L8. Single Language Interface: The system's user interface, error messages, notification templates, and documentation are developed exclusively in English. Dynamic multi-language translation or localization for other languages (e.g., Vietnamese, Japanese) is not supported in the current version.
3.3. Compatibility Limitations:
L9. Modern Browser Requirement: The system's UI/UX is designed, tested, and optimized exclusively for modern evergreen web browsers: Google Chrome (v90+), Microsoft Edge (v90+), Mozilla Firefox (v88+), and Apple Safari (v14+). Legacy browsers, most notably Internet Explorer 11 and older versions, are explicitly unsupported and may exhibit layout rendering errors or JavaScript incompatibilities.
L10. Responsive Web Only (No Native Mobile App): While the system's web interface is responsive and adapts to different screen sizes (desktop, tablet, mobile), it is not a native mobile application. Push notifications, biometric authentication, and other mobile-native features are not available.
4. Exclusions
E1. Financial, Payroll, & Compensation Management: The system strictly manages the academic training lifecycle. It completely excludes any features related to tracking, calculating, or disbursing internship allowances, stipends, enterprise payroll, tax documentation, social insurance, or any form of financial compensation for the students or enterprises.
E2. Legal Contract & Digital Signature Management: The system excludes the drafting, storage, verification, or management of legal internship employment contracts, Non-Disclosure Agreements (NDAs), or any documents requiring legally binding digital signatures (e.g., DocuSign, Adobe Sign) between the Student and the Enterprise.
E3. General-Purpose Job Board or Alumni Recruitment: The platform is designed exclusively for the structured academic OJT semester. It will not function as a general-purpose post-graduation job recruitment portal, alumni career services platform, or freelance marketplace. Job postings are strictly limited to internship positions within the context of an active University semester.
E4. AI-Powered Automated Screening or Grading: While the system manages the end-to-end recruitment and grading workflows, it explicitly excludes the use of Artificial Intelligence (AI), Machine Learning (ML), or Natural Language Processing (NLP) to: automatically screen or rank student CVs, auto-grade the textual content of weekly or final reports, or generate automated feedback.
E5. Background Verification & Security Checks: The system does not perform criminal record checks, financial credit checks, academic integrity investigations, or any form of deep background verification on students on behalf of Enterprises. Such verifications, if required, must be conducted independently by the Enterprise through their own HR processes.
E6. Enterprise Internal HR & Operations Management: The system's scope is strictly limited to the student's internship lifecycle within the university-enterprise partnership. It excludes features for managing the enterprise's internal HR workflows (employee attendance tracking, internal performance reviews, project management tools, or enterprise-level reporting unrelated to student interns).
E7. Third-Party Single Sign-On (SSO) Integration: Integration with external identity providers such as Google SSO, Microsoft Azure Active Directory, Facebook Login, or university-specific LDAP/CAS authentication systems is excluded from the current project phase. All authentication is handled internally (see Dependency D8).
E8. Automated Notification Escalation & SLA Enforcement: The system provides basic notification dispatching (email alerts, in-app notifications) but does not enforce Service Level Agreements (SLAs). For example, if an Enterprise fails to review a weekly report within 7 days, the system will not automatically escalate the issue, reassign the student, or impose penalties. Such escalations require manual intervention by the Training Manager.
